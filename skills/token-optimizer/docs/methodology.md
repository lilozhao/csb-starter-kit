# 方法论 · Token 消耗体检与优化

> 2026-09-12 首次在若兰（OpenClaw 实例）上实测并落地。数字都是真实账单口径（会话 JSONL 里的 `usage`）。

---

## 一、核心公式

```
成本 = 调用次数 × 每次携带的上下文
```

实测（若兰，近 3 天 5720 次调用）：

| 项 | 值 |
|---|---|
| `cacheRead` 中位数 | **207,360 token/次** |
| 新鲜输入 均值 | 3,315 token/次 |
| 输出 均值 | 463 token/次 |

**结论：输出和新鲜输入都是零头，钱全在"每次都要重新携带的上下文"。**

---

## 二、数据从哪来

OpenClaw 会把每次模型调用的 usage 记在会话文件里：

```
~/.openclaw/agents/<agent>/sessions/<sessionId>.jsonl
每行 message.usage = { input, output, cacheRead, cacheWrite, totalTokens }
```

`scripts/lib.js` 就是读这个。**不需要任何 API key，也读不到内容之外的隐私**（只看计数）。

## 三、四类问题与判据

| # | 问题 | 判据（默认阈值） | 典型病因 |
|---|---|---|---|
| 1 | 会话上下文膨胀 | 单次 `cacheRead` > 80K | 会话长期不归档（27 天 = 9223 条消息 = 168K） |
| 2 | 调用密度高 | > 200 次/天 | 工具一条一条跑；重复验证；轮询 |
| 3 | cron 灌主会话 | `main` 任务数 > `isolated` | 纯脚本任务写成 `systemEvent → main` |
| 4 | 工作台文件过肥 | 注入 md 合计 > 40KB | HOT 层没分层，长文堆在必读文件里 |

---

## 四、五步优化（按收益排序）

### 1) 归档膨胀会话 —— 最大收益

单次从 168K → ~30K，**省 ~80%**。

代价：会话连续性靠 `MEMORY.md` + `memory/` 日期文件 + archive 承接；`memory_search` 仍能检索到归档内容。
**关键**：归档前先确认记忆已落文件（否则细节会随会话一起"沉底"）。

### 2) 减少工具往返 —— 直接砍次数乘数

每次工具调用 = 一次全额上下文付费。所以：

- 一条命令干多件事（写脚本跑完，而不是一条一条查）
- 不重复验证已确认的结论
- 大文件定向读（offset/limit、grep），不整篇读
- 长任务一次长 poll，不循环短查询

### 3) cron 改道 isolated

`systemEvent → main` 的纯脚本任务 → `agentTurn → isolated` + `lightContext`。

实测：主会话事件 24 → 10 次/天；每次省下差量（主会话 168K vs isolated 几 K）。

代价：isolated 任务看不到主会话的对话上下文——所以**只改"跑脚本就完事"的任务**，需要对话连续性的（早安问候、待办追踪）留在 main。

### 4) 工作台文件瘦身

实测 70.5KB → 31.8KB（-55%），约 30K token → 13K token。

做法：**HOT 层只留核心 + 指针（≤100 行）**，正文原文 `cp` 进 `memory/archive/` 或 `docs/archive/`（可检索，可回滚）。

代价：细节不再"免费"出现在每次上下文里，需要时得检索一次（这本来就是分层记忆的设计意图）。

### 5) 心跳参数化

配置（`agents.defaults.heartbeat`）：

```json
{ "every": "45m",
  "activeHours": { "start": "07:30", "end": "23:00", "timezone": "Asia/Shanghai" },
  "lightContext": true,
  "isolatedSession": true }
```

- `lightContext` + `isolatedSession`：心跳不再吃主会话满额上下文（这是**单次最大的单项节省**之一）
- `activeHours`：夜间静默
- `every`：按需降频

代价：心跳响应变慢（45 分钟粒度）；夜间若有紧急告警需另设 cron 兜底。

---

## 五、免费收益：缓存友好

多数供应商的 `cacheRead` 单价远低于新鲜输入（常见 ~1/10）。
**保持上下文前缀稳定**（文件顺序、避免频繁小改必读文件）能提高缓存命中率——
反之，频繁改动必读文件会**打断缓存**，把便宜的部分变成贵的。这条常被忽略。

---

## 六、诚实的局限

1. `cacheRead` 数字来自本地会话记录，**不等于**供应商账单（各家计费口径、缓存折扣不同）
2. 粗略 token 估算用「字节/2.5」（中英混排），会有偏差
3. cron 改道是**语义判断**（"这个任务需不需要对话上下文"），工具只能给候选，最终要人或 agent 判断
4. 会话归档会**永久分离**对话连续性，务必先确认记忆已落盘
5. 若审计本身频繁运行，也会产生调用——建议**每天一次**，别进心跳高频循环

## 七、跨实例协作补充（2026-09-12，实况见 `case-cross-agent.md`）

在另一个实例上跑通后新增的三条判据/纪律：

1. **口径先对齐**：`cacheRead` 一律以 **token** 计。对方报"207.3 KB"而我方中位是 207,360 token——
   不对齐的话，收益估算会差 1000 倍。（换数据时必须显式写单位）
2. **看"隔离度"而非绝对数**：`isolated : main` 的比值比任务总数更能反映 cron 卫生
   （例：对方 12:7 已合格，我方 16:4）。
3. **先确认"我在跟谁说话"**：跨实例协作前核对注册表映射（本次出现条目名与回执署名不一致的情况），
   否则数据归属都会错。
4. **同款症状 ≠ 同款处方**：对方 md 更瘦、cron 已占优，所以第一优先级只有"归档会话"一条；
   建议必须**基于对方数据排序**，不能照搬自己的清单。

> 协作边界：**信息可自由流动，动作永远由对方决定**。不向其他 agent 发可执行指令，
> 不代跑、不代装；对方要装技能须经其人类主人授权。
